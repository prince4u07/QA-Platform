Read this first: your tests are not the problem

The full suite runs in 11 seconds on 8 workers. Your budget is 300. The tests consume 4% of it, and I could not make them flake in five consecutive parallel runs, which is 610 test executions without a single false failure.

So the five minute target will not be won or lost in your test code. It will be won or lost in environment setup, because Chromium alone is a 111 MB download. Get the caching right and you finish in about a minute. Get it wrong and you will blow the budget every push while your tests sit there taking eleven seconds.

1 CI pipeline integration

Two jobs, not one. A fast gate that fails within seconds on the obvious, and the full suite behind it. Developers get a verdict on a typo long before the browsers have finished starting.

Where the time actually goes

StageColdCachedNotes
Checkout~3s~3s
Python + dependencies~25s~5suv, cache keyed on requirements.txt
Chromium download~45s~2s111 MB, cache keyed on the Playwright version
Test run, 4 workers~16s~16sSlower than your 11s: CI runners have 4 cores, not 12

The workflow

name: CI
on: [push, pull_request]

jobs:
  fast-gate:              # fails in seconds on lint or a broken import
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: { enable-cache: true }
      - run: uv pip install --system -r backend/requirements.txt
      - name: Unit tests only
        run: pytest -m "not browser" -q
        working-directory: backend

  full-suite:
    needs: fast-gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: { enable-cache: true }
      - run: uv pip install --system -r backend/requirements.txt

      - name: Cache Chromium          # the single biggest win
        uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: pw-${{ runner.os }}-${{ hashFiles('backend/requirements.txt') }}
      - run: playwright install --with-deps chromium

      - name: Full suite
        run: pytest -n 4 -q
        working-directory: backend
Do

Key the browser cache on the Playwright version, which is pinned in requirements.txt. Keying it on the lockfile alone means every unrelated dependency bump re-downloads 111 MB.

Never

Do not add a MySQL service container. Your suite does not touch the database. This was confirmed by running the whole suite green while the MySQL service was stopped, on 13 August, when it stood at 112 tests. Adding a database service would cost 15 to 20 seconds per run to serve no test at all.

2 Flake mitigation

You asked for zero false failures. That is achievable and you are close to it already. Five consecutive 8-worker runs produced 610 test executions and zero failures.

Fixed sleeps are the enemy, and you still have five

A time.sleep() is a bet that the machine will be fast enough. On a loaded CI runner it loses, and the test fails for reasons that have nothing to do with your code. That is precisely the false failure you want to eliminate.

Two were removed today by making the values configurable rather than hardcoded, which cut the suite from 37s to 30s serial before parallelism was even applied:

What was hardcodedBeforeAfterFix
Step timeout, 8s, waiting to prove a step fails8.79s2.30sQA_STEP_TIMEOUT_MS
Manual watch poll, 1.5s per loop10.49s4.72sWATCH_POLL_SECS

Five fixed sleeps remain in the crawler and manual runner. Each one is a latent false failure. The rule that replaces them: wait for a condition, never for a duration.

Never

time.sleep(1.5) then assume the page is ready.

Instead

locator.wait_for(state='visible', timeout=...), which returns the instant the condition is true and fails loudly with a real reason when it never becomes true.

Network isolation, already solved

Your browser tests start a disposable HTTP server inside the test on port 0 and point Chromium at it. That is a better answer than mocking: nothing is faked, but nothing external is depended on either. It is the reason the suite does not flake.

Rule

No test may contact a real website. The moment one does, your pipeline's reliability becomes that site's uptime. Enforce it in review; a test that needs the internet belongs in a separate, non-blocking job.

Database isolation, for when you need it

You do not need this yet, but when tests start touching MySQL: give each test a transaction and roll it back at the end. It is the same technique already used to verify the schema by replaying the application's real SQL and rolling back, which leaves no residue. Shared truncation between tests breaks the moment you parallelise; transactions do not.

When a flake does appear

It will eventually. The response matters more than the prevention.

  • Do not add a blind retry. pytest-rerunfailures turns a visible flake into an invisible one. The test still lies, you just stop hearing about it.
  • Quarantine, then fix. Mark it, move it out of the blocking job, open an issue with the run log. The pipeline stays trustworthy while the flake gets diagnosed.
  • Track the rate. A flake rate you measure is manageable. One you do not is how teams end up ignoring red builds.

3 Test isolation

You asked about running tests in isolated Docker containers. For this suite that would be the wrong call, and the numbers say so clearly.

Do not containerise per test

A container start is roughly 1 to 2 seconds. At 122 tests that is two to four minutes of pure startup, to replace isolation you already have. Your entire suite currently runs in 11 seconds. Per-test containers would make it fifteen times slower and consume most of your five minute budget doing nothing.

One container for the whole job is the right granularity, and that is exactly what a GitHub Actions runner already gives you.

Process isolation is already doing the job, and it is doing it for free:

  • Separate processes per worker. pytest-xdist gives each worker its own Python process, so module state cannot leak between them.
  • Port 0 for test servers. The OS assigns a free port, so two workers running browser tests simultaneously never collide.
  • tmp_path for files. Screenshot and manual run directories are redirected per test, so nothing is written to shared disk.

That combination is why all 122 tests pass on 8 workers with no changes. The proof is the five clean runs, not the theory.

What would break it

Two pieces of shared state to keep an eye on as the suite grows. Neither is a problem today because tests use distinct identifiers, but both would bite if that stopped being true:

  • manual_run._active, a module-level dictionary of live sessions keyed by test case id. Two tests using the same id in one process would fight over it.
  • Routes registered on the shared Flask app at import time in test_app.py. Safe across processes, but it means route registration order is not something to depend on.

Finding

-n auto is 60% slower than -n 8 on this machine. Each browser test spawns a Chromium process, so at one worker per core the browsers compete with the workers for CPU. Set the worker count explicitly to roughly two thirds of the cores, and re-measure on the runner rather than assuming your laptop's number transfers.

Sharding: not yet

Splitting the suite across several CI machines is the standard answer to a slow suite. Yours is 11 seconds. Sharding it would add more machine startup time than it saves, and give you several logs to read instead of one. Revisit when the suite passes about two minutes, at which point split by the marker below rather than by file count, so each shard has a similar browser workload.

The one change worth making now

Mark the browser tests, so the fast gate can skip them and return in about a second.

# pytest.ini
markers =
    browser: needs a real Chromium instance

# and on the browser test modules
pytestmark = pytest.mark.browser

That splits your 122 tests into roughly 95 that need nothing and 27 that need a browser. A developer who breaks a scoring rule hears about it before Chromium has even started.

5 On "zero false passes"

Zero false failures is a reasonable target and you are effectively there. Zero false passes is not something any test suite can promise, and I would be misleading you to say otherwise. A false pass is a bug in an area no test covers, and no suite can prove the absence of those. Green means "nothing I checked is broken", never "nothing is broken".

What you can do is shrink the space where a false pass can hide:

  • The React interface has no unit tests at all. It is checked by lint and a successful build, which catch a broken import and nothing about behaviour. This is by far the largest blind spot in the project.
  • No test touches MySQL. Convenient for CI speed, but it means a broken query reaches production. One integration job, allowed to be slower and run on merge rather than every push, would close that.
  • Coverage is not measured. Adding pytest-cov tells you which branches nothing exercises, which is where false passes live.

Name these in your pipeline documentation rather than implying the green tick covers everything. A team that knows where the gaps are makes better decisions than one that trusts a badge.
