6.1 Conclusion

QA Platform set out to replace a scattered, manual, multi-tool quality assurance process with a single automated workflow, and it does that. A user registers a website, runs an audit, and reads consolidated results in one place, including the pages behind a login that most automated tools cannot reach.

The system drives a real Chromium browser through Playwright, crawls the target, and applies nine categories of checks to every page it visits. Each finding is graded by its own severity and rolled into a health score that can be compared between runs. All of the analysis logic is written within the project. The single external component is axe-core, the open source accessibility engine, which is bundled in the repository and injected into each page rather than re-implementing the WCAG rule set. No external service is contacted to perform any test.

Capabilities beyond the original scope

Four capabilities emerged during development that were not in the original plan, each answering a weakness the earlier design could not:

  • Executable test steps. Steps written in plain English are performed by the browser, so the platform detects functional failures and broken multi-step workflows. A crawler alone cannot tell that a login form rejects a valid password while every page still returns 200.
  • Regression detection. Each run is compared against the previous run of the same test case and reports what is newly broken, what is fixed, and how the score moved.
  • Performance measurement. Real page weight and load timings, with thresholds that name the oversized files responsible.
  • A manual tester workspace. The written steps become a live checklist, issues are reported against the exact page and screenshot on screen, and automated checks run on every page the tester walks through.

The system is verified by 136 automated tests, 129 covering the backend and 7 covering the interface, including tests that drive a real browser against a disposable website generated by the test itself. The suite runs in about eleven seconds and found genuine defects during development, among them a health score that rated every real website as zero and a crash that took down the reports dashboard when one endpoint returned no data.

6.2 Limitations of the System

Stated plainly. Knowing where a system is weak is more useful than a list of what it does well, and every item below is a specific, checkable claim rather than a general caveat.

Depth of detection

  • The SEO check is shallow. It verifies that a page has a title and nothing else. Meta descriptions, heading structure, viewport declaration and indexing directives are not inspected, so a page can pass the SEO category while being poorly optimised.
  • The security check covers four things. HTTPS usage and three response headers. Mixed content and insecure cookie flags are not detected, and a browser warning about mixed content is currently filtered out of the console results.
  • Mobile checks are skipped on authenticated crawls. A logged-in session runs in a desktop viewport, where measuring tap targets would flag every ordinary control. The run says so in its coverage notes, but the gap is real.
  • Two checks are capped per page. Thirty links and fifty tap targets. Larger pages are only partially examined. The report states what was skipped, so a partial result is never presented as a clean one.
  • Accessibility correctness is inherited. The platform trusts axe-core's verdicts. What it verifies is that those verdicts are carried through to severity and scoring correctly, not that axe-core is itself right.

Reliability and engineering practice

  • Flakiness is not detected. If a page is caught mid-render, the resulting finding is reported as a new regression, indistinguishable from a genuine one. Nothing re-checks a finding before calling it new.
  • The project is not under version control and has no continuous integration, so tests are run by hand and there is no history of changes.
  • Interface testing is thin. Seven behavioural tests covering one page. The remaining pages, including test case management and the bug tracker, have no behavioural coverage.
  • Errors are frequently swallowed. 132 broad exception handlers return a generic message, which makes diagnosis harder than it should be.

Scale and deployment

  • Single machine, two crawl workers. Designed for one user at a time. No load or concurrency testing has been carried out.
  • Captured login sessions are stored as plain files on disk, unencrypted. This is acceptable for local use and would not be for a shared deployment.
  • MySQL must be started manually and the platform reports the database as unreachable when it is not running.
  • The AI assistant requires an API key and internet access. Without them the testing features work unchanged and only the assistant is unavailable.
  • Static site upload was removed. Testing is against live URLs only.

6.3 Future Scope of the Project

Ordered by what would add the most value for the least work, using the limitations above as the agenda rather than a wish list.

Immediate · closing known gaps
  • Complete the SEO and security checks. Meta description, heading structure, viewport and indexing directives; mixed content and cookie flags. The framework already supports them, so this is filling in rules rather than new architecture.
  • Version control and continuous integration. Running the suite automatically on every change, which turns 136 tests from something run by hand into a genuine safety net.
  • Behavioural tests for the remaining pages, extending the pattern already established for the reports dashboard.
  • Mobile checks on authenticated pages, by running a second pass in a mobile viewport while holding the same session.
Near term · trustworthiness
  • Flake detection. Re-verify a finding before reporting it as new, and mark one that does not reproduce as unstable rather than as a regression. This is what makes regression detection safe to act on automatically.
  • Scheduled runs. Nightly audits against registered projects, so quality is tracked continuously instead of only when someone remembers to click Run.
  • Visual regression testing. Comparing screenshots between runs to catch layout breakage, which is currently the largest class of defect only a human can see.
  • Coverage measurement, to show which parts of the analysis engine no test exercises.
Longer term · scale and reach
  • Cross-browser testing. Playwright already supports Firefox and WebKit; the engine is written against a browser interface, not Chromium specifically.
  • Team collaboration. Shared projects, assignment and roles, since the database already carries a role for every user.
  • Issue tracker integration. Pushing confirmed defects into Jira or GitHub Issues instead of keeping them only in the built-in tracker.
  • Distributed crawling, splitting a large site across several workers to keep audit times reasonable on sites of thousands of pages.
  • Self-healing selectors that learn. The steps engine already tries several strategies to find an element; recording which one succeeded would let it adapt to a redesigned interface instead of merely surviving one.

Taken together these would move the platform from a working single-user tool to something a team could rely on continuously. The foundations for most of them are already in place, which is the more useful outcome of the work: the architecture did not have to be worked around to identify any of the above.
