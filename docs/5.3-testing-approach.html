A platform whose purpose is finding defects has to be able to show that it works. The testing strategy is therefore built on execution rather than description: every claim below corresponds to a test that runs on demand and either passes or fails.

Testing is organised in four layers, each answering a different question. The first three are separated by how much of the real system they exercise. The fourth cuts across all of them.

5.3.1 Unit testing

Question: is each rule correct in isolation? The analysis engine is built from pure functions, which makes them testable without a browser or a database. Findings are fed in as controlled inputs and the output is checked exactly. 77 tests, running in under a second.

This layer covers severity grading, the health score, the regression comparison, the performance thresholds and the parser that turns written steps into browser actions.

  • test_worse_site_always_scores_lower_than_bad_site
  • test_critical_finding_costs_more_than_a_minor_one
  • test_finding_severity_uses_the_value_the_check_assigned
  • test_first_run_is_a_baseline_not_a_regression
  • test_url_assertion_beats_the_generic_text_assertion

5.3.2 Integration testing

Question: do the parts work once assembled? These exercise the Flask application itself: routing, authentication, rate limiting, error handling and the background job manager that keeps the interface responsive during a crawl. 8 tests.

  • test_key_routes_registered
  • test_login_rate_limit_trips_429
  • test_job_runs_to_done
  • test_job_marks_failed_on_error_code

5.3.3 Real-target testing

Question: does it hold up against a real browser and a real site? The most important layer. A disposable HTTP server is started inside the test, serving pages with genuine defects built in: a link that returns 404, an oversized script, a button with no label, a login form that only accepts one password. A real Chromium browser is then driven against it. 27 tests.

Because the target is generated by the test itself, results are exact and repeatable, and no external website is depended upon.

  • test_a_real_login_workflow_runs_end_to_end
  • test_a_wrong_password_is_caught_as_a_functional_failure
  • test_performance_measures_a_real_page
  • test_every_finding_carries_a_severity
  • test_a_multi_page_workflow_crosses_pages

5.3.4 Error handling

Question: what happens when something goes wrong? A testing tool that crashes on a hostile page is worse than useless, so failure paths are tested as deliberately as success paths. These tests are distributed across the three layers above rather than kept separately.

Covered: a database that is switched off, a page that blocks measurement, a screenshot that cannot be written, a workflow step that breaks halfway, a test case deleted while its crawl is running, an expired login session, and navigation inside a single-page application.

  • test_database_being_down_says_so_instead_of_internal_server_error
  • test_a_genuine_bug_is_still_a_500_and_leaks_nothing
  • test_performance_survives_a_page_that_blocks_evaluate
  • test_a_broken_screenshot_callback_does_not_fail_the_step
  • test_steps_after_a_break_are_skipped_not_re_reported

5.3.6 Defects found by this process

Tests were written from the requirement and confirmed to fail against the unfixed code before the fix was made. Two examples where this caught defects that manual inspection had missed.

The health score was unusable for tracking quality

The score was calculated as 100 - (issue count × weight), clamped at zero. Any real website reached zero immediately, so a site with 20 problems and a site with 200 scored identically. This defeated the objective of tracking quality across releases.

Replaced with a severity-weighted model using diminishing returns. The same three sites now score 80, 57 and 39 instead of 0, 0 and 0.

Caught by: test_worse_site_always_scores_lower_than_bad_site

Manual runs could never crawl beyond the opening page

The page limit for manual test cases was stored as 1. Since the landing page is captured before crawling begins, the loop condition pages < limit was already false and the crawl exited without visiting a single additional page.

A stored limit of 1 is now treated as unset, and the limit is exposed in the interface for both test types.

Caught by: test_a_manual_run_can_crawl_past_the_landing_page

5.3.7 Reproducing these results

The full suite runs from the backend directory with a single command and needs no database, no network access and no configuration.

# from backend/
python -m pytest

............................................................ [100%]
112 passed in 79.80s

The database layer is verified separately by replaying the application's actual SQL statements against MySQL 8.0 inside a transaction that is rolled back, which confirms the schema matches the queries without leaving any test data behind.

5.3.8 Limits of the current suite

Stated plainly, since knowing what is not covered matters as much as knowing what is.

  • The React interface has no unit tests. It is verified by static analysis and a successful production build, which catches broken references but not incorrect behaviour.
  • A manual run against a real logged-in website has not been automated. It requires a visible browser and live credentials, so it is exercised by hand.
  • Accessibility results depend on axe-core. Its correctness is assumed rather than retested; what is tested is that its severity ratings are carried through to the score correctly.
  • No load or concurrency testing has been done. Crawls are limited to two background workers, which has not been stressed beyond ordinary use.
